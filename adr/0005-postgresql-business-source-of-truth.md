# ADR-0005：PostgreSQL 作为 Platform 业务事实来源

- 状态：Accepted
- 日期：2026-09-09
- 决策者：ArchGuard 项目所有者
- 替代：无

## 背景

V1 需要可靠保存 Project、Repository、Policy、Scan 生命周期、结果引用和审计关系，并支持授权范围内的一致查询与幂等状态更新。G2 已接受 PostgreSQL 只由 Platform 访问并作为业务事实来源，但此前缺少独立 ADR。

## 决策驱动因素

- 业务对象和授权关系需要事务、一致性约束、索引和可审计迁移。
- Platform 初期为模块化单体，多个领域可在同一事务内保持关键不变量。
- Scanner、Gateway 和外部客户端不能直接访问业务数据库。
- 当前没有缓存、Broker、文档数据库或每模块独立数据库的容量证据。

## 选择

- PostgreSQL 是 Platform 业务事实的唯一持久来源；Project、Repository、Policy、Scan、持久化结果和业务审计均以其已提交状态为准。
- 只有 Platform 基础设施适配器可以连接数据库；Scanner、Analyzer、Gateway、Samples、Evals 和外部客户端禁止直连。
- 每个 Platform 模块拥有自己的表和持久化映射；模块不得直接读取或写入其他模块的表来绕过公开应用接口。
- Schema 变化只通过按序、不可改写的 Flyway 迁移发布；验证空库和上一受支持版本升级路径。
- 事务边界位于应用层。创建 Scan 时先持久化业务状态，再由后台执行器认领；初期任务可靠性可以使用 PostgreSQL 记录，不预先引入 Broker。
- Redis、搜索引擎、对象存储或只读副本未来只能作为派生/辅助存储，不能在没有一致性设计时成为第二业务事实来源。

## 备选方案

- 仅使用内存或文件：无法提供重启恢复、并发事务和可靠迁移，拒绝。
- MongoDB/其他文档数据库：能保存文档，但当前关系、约束和事务用例没有证明其更合适，拒绝。
- Redis 作为主存储：适合缓存和部分队列场景，不适合作为当前业务事实与审计来源，拒绝。
- 每个模块独立数据库：隔离更强，但会提前引入跨库一致性和运维成本，拒绝。
- Kafka/Broker 作为 Scan 任务事实：可以传递事件，但不能替代业务状态；没有 M7 可靠性证据前不引入。

## 正面影响

- 授权、幂等、Scan 状态和结果关联可以使用事务与数据库约束保持一致。
- 备份、恢复、迁移和审计有单一可定位事实来源。
- Scanner 与 Gateway 无数据库权限，跨进程边界更清晰。

## 负面影响与风险

- PostgreSQL 成为 Platform 的关键依赖，需要健康、容量、备份、恢复和迁移治理。
- 同库容易诱发跨模块表访问，必须用代码所有权、架构测试和数据库权限/Schema 约定约束。
- 大型结果或高吞吐任务未来可能需要派生存储或消息机制，但必须处理一致性与回滚。

## 验证方式

- M2/M3 使用真实 PostgreSQL 兼容实现运行模块与集成测试，不以纯内存替代证明持久语义。
- 每次迁移验证空库初始化和上一受支持版本升级；已发布迁移内容不可修改。
- 状态机、幂等、并发认领和迟到结果测试证明事务不变量。
- 架构/集成测试证明 Scanner 和 Gateway 不拥有数据库连接，模块不跨边界写表。
- M11 实际演练备份、恢复和应用回滚，并记录恢复点和兼容边界。

## 何时重新评估

- 已测量的数据规模、查询、吞吐或恢复目标无法由合理 PostgreSQL 设计满足。
- 出现需要独立合规隔离、区域边界或服务提取的数据所有权证据。
- M7 证明数据库任务认领是可靠性瓶颈，并有 Broker 的故障恢复和回滚收益。

新增缓存、Broker、搜索或对象存储必须说明派生数据重建、一致性、权限、迁移和回滚；替换业务事实来源须由新 ADR 取代本决策。
