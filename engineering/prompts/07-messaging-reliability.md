# 阶段 7：消息与可靠性演进

## 阶段目标

基于真实容量和故障数据决定是否保留数据库队列或引入消息系统；只有复杂度收益有证据时才实施 Kafka、RabbitMQ 或其他中间件。

## 输入与范围

- 必需：当前任务吞吐、延迟、失败、重试、数据库负载和恢复数据。
- 必需：ADR，比较数据库队列、RabbitMQ、Kafka 和维持现状。
- 非目标：没有基线就迁移、为展示技术增加基础设施、同时重写业务状态机。
- 涉及 Platform、Scanner 和 Deploy 时必须记录版本与发布顺序。

## 开始前检查

1. 运行现有队列容量和故障测试，保存可复现基线。
2. 定义 SLO：排队时间、端到端耗时、成功率、恢复时间和可接受重复率。
3. 区分业务状态、传输状态和观测状态，明确事实来源。
4. 估算消息大小、峰值速率、保留期、分区键和顺序需求。
5. 识别运维能力、成本、备份和本地开发影响。

## 执行流程

### 7A：只读评估与 ADR

1. 描述当前数据库队列瓶颈及其证据。
2. 比较候选方案的投递语义、顺序、扩展、运维、安全和成本。
3. 记录“不引入新中间件”作为有效备选。
4. 定义触发重新评估的量化阈值。
5. 若现有方案满足 SLO，结束阶段并只提交 ADR 和基线报告。

### 7B：有条件实施

仅在 ADR 接受新消息系统后执行：

1. 定义事件 Schema、版本、所有者和兼容范围。
2. 使用 Outbox 保证业务事务和消息发布之间的一致性。
3. 消费者按业务幂等键去重，假设至少一次投递。
4. 定义指数退避、最大重试、不可重试错误和死信。
5. 提供安全的死信检查与重放流程，重放必须审计。
6. 传播 traceId、actorId、projectId 和 scanJobId。
7. 限制消息大小；消息不得携带完整源码或凭据。

### 7C：迁移与运维

1. 支持旧队列和新通道短期共存，避免一次切换。
2. 定义生产者、消费者、Deploy 和数据库迁移的顺序。
3. 为积压、消费延迟、失败率、重复和死信建立指标与告警。
4. 编写 Broker 不可用、消费者崩溃和消息重放 Runbook。
5. 明确回退到旧队列时如何处理在途消息。

## 交付物

- 容量/失败基线和 ADR。
- 若实施：版本化事件、Outbox、幂等消费者、重试、死信和重放工具。
- 兼容矩阵、迁移计划、Dashboard、Runbook 和故障测试报告。

## 验证

1. 重复消息、乱序、消费者崩溃、提交前后故障测试。
2. Broker 超时/不可用、网络抖动和积压恢复测试。
3. 至少一次投递下业务结果不重复。
4. 对比变更前后的吞吐、P95/P99、恢复时间和运维成本。
5. 验证无消息包含敏感源码或凭据。

## 停止条件

没有可复现基线、ADR 未接受、消息语义不清楚、无法保证幂等或缺少可执行回滚路径时不得实施新中间件。

## 退出条件

要么有证据地保留数据库队列，要么新方案达到 SLO 且故障恢复、兼容、监控和回滚全部经过验证。
