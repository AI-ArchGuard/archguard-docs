# 阶段 1：产品与架构文档

## 阶段目标

只修改 `archguard-docs`，让新开发者在十分钟内理解 ArchGuard 服务对象、解决的问题、MVP 边界、七仓库关系和主要技术取舍。

## 输入与范围

- Issue：`<issue-number>`
- 相关访谈、目标岗位或作品集约束：`<related-spec>`
- 允许修改：product、requirements、architecture、adr 及必要索引。
- 非目标：不实现代码、不确定尚无证据的性能指标、不承诺商业化和多语言全覆盖。

## 开始前检查

1. 盘点现有产品、架构、ADR 和术语文档，避免建立重复事实来源。
2. 阅读七个仓库 README，核对职责与非职责。
3. 将未知信息标为开放问题，不用假设冒充已确认需求。
4. 建立需求、架构决策、仓库和里程碑之间的追踪表。

## 执行流程

### 1A：产品定义

1. 编写产品章程：问题、目标用户、使用场景、价值、成功指标和防护指标。
2. 区分 MVP 目标、非目标、假设和外部依赖。
3. 描述核心用户旅程：注册项目、登记仓库、触发扫描、查看证据、PR 反馈。
4. 编写 MVP Feature Spec，给每项需求稳定编号和可验证验收标准。
5. 创建术语表，统一 Project、Repository、Scan、Violation、ADR、Tool 等概念。
6. 制定 12 个月路线图，按结果而非技术组件描述里程碑。

### 1B：总体架构

1. 绘制 C4 System Context，标出用户、GitHub、模型提供方和信任边界。
2. 绘制 Container 图，说明 Platform、Scanner、Gateway、数据库和部署边界。
3. 编写七仓库职责矩阵、依赖方向和禁止依赖。
4. 定义对外 REST、Scanner Schema、MCP Tool Schema 和部署兼容矩阵的所有者。
5. 描述关键数据流、敏感数据分类、保留期和删除责任。
6. 补充核心流程和失败流程的时序图。

### 1C：架构决策

至少分别记录以下 ADR：

- Platform 初期采用模块化单体。
- PostgreSQL 作为业务事实来源。
- 确定性规则优先于 LLM 判断。
- Scanner 使用独立、版本化契约。
- MCP 工具默认只读和最小权限。

每份 ADR 必须包含背景、驱动因素、选择、备选方案、正负影响、验证方式和重新评估条件。

## 交付物

- 产品章程、MVP Feature Spec、术语表、路线图。
- C4 图、仓库边界、契约所有权和关键流程文档。
- ADR 文件及 ADR 索引。
- 需求—架构—里程碑追踪矩阵。

## 验证

1. 检查 Markdown 和 Mermaid 语法、相对链接与索引。
2. 从陌生开发者视角执行十分钟阅读演练。
3. 确认每个需求都有验收标准，每个关键取舍都有 ADR。
4. 检查所有目标均有对应非目标，所有敏感数据都有处理规则。
5. 对照七仓库 README，确保职责描述一致。

## 停止条件

产品目标、目标用户、数据处理边界或公开部署范围存在会改变总体架构的歧义时停止并请求决定。

## 退出条件

文档可独立解释产品、范围、系统结构和主要取舍；链接有效；开放问题有 Owner 或后续 Issue。
