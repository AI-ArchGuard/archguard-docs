# 阶段 12：性能与 Kubernetes

## 阶段目标

先为 Scanner、Platform 和 MCP Gateway 建立可复现性能基线并优化真实瓶颈；只有单机或 Compose 部署限制有量化证据时，才引入 Kubernetes 或 Helm。

## 输入与范围

- 必需：性能目标、真实或合成工作负载、运行环境和阶段 11 的稳定部署。
- 必需：Kubernetes 决策 ADR；允许结论为“不引入”。
- 非目标：无数据优化、只展示 QPS、不记录硬件、用 Kubernetes 掩盖应用问题。
- 云集群创建和费用性资源必须单独授权。

## 开始前检查

1. 定义用户旅程、峰值并发、数据规模、扫描大小和 MCP 调用模型。
2. 定义吞吐、P50/P95/P99、错误率、资源和成本指标。
3. 固定代码提交、配置、数据集、硬件、预热和测量时长。
4. 检查日志、指标和 Profiling 能定位瓶颈。
5. 记录当前容量和预计增长，不预设 Kubernetes 是答案。

## 执行流程

### 12A：可复现基线

1. 为 Scanner 固定文件数、节点、边和规则组合。
2. 为 Platform 固定 API、数据库数据量、读写比例和并发。
3. 为 Gateway 固定工具分布、下游延迟、响应大小和会话并发。
4. 多次运行，保留原始摘要、环境和波动范围。
5. 记录 CPU、内存、GC、连接池、数据库和网络指标。

### 12B：瓶颈分析与优化

1. 使用 Profile、慢查询和追踪定位最大瓶颈。
2. 一次只应用一个可解释优化，先写性能或回归测试。
3. 比较优化前后结果，同时观察正确性、资源和成本。
4. 防止缓存污染、过度并发、Goroutine 泄漏和数据库热点。
5. 没有量化收益的优化应撤销或记录原因。

### 12C：Kubernetes 决策门禁

ADR 至少比较：

- 保持单机/Compose 并纵向扩展；
- 托管容器平台；
- Kubernetes manifests；
- Helm 管理的 Kubernetes。

只有存在高可用、弹性、滚动升级、多实例调度或环境治理等明确需求，并证明收益大于运维成本时才接受 Kubernetes。

### 12D：有条件实施 Kubernetes

1. 保留 Docker Compose 作为最低启动方式。
2. 提供 Deployment、Service、Ingress、Secret 引用、ConfigMap 和命名空间策略。
3. 配置 startup/readiness/liveness 探针、资源 requests/limits 和安全上下文。
4. 数据库优先使用受控外部服务；不得用临时容器文件系统保存事实数据。
5. HPA 必须基于测得指标和容量测试，不使用随意阈值。
6. 设置 PodDisruptionBudget、滚动策略和优雅终止。
7. Helm 值按环境分层，模板不得包含 Secret。
8. 更新网络暴露、RBAC、镜像摘要、监控和 Runbook。

## 交付物

- 三个核心组件的性能基线、工作负载和复现脚本。
- Profile、优化记录及前后对比报告。
- Kubernetes 决策 ADR。
- 若接受：Manifests/Helm、部署文档、容量和故障演练报告。

## 验证

1. 在固定环境重复性能测试并报告方差。
2. 功能和契约测试确保优化未改变行为。
3. 压力、容量、长稳、超时和资源耗尽测试。
4. 若实施 Kubernetes：模板渲染、策略/Schema 检查和隔离集群部署。
5. 验证滚动升级期间核心请求、任务租约和优雅关闭。
6. 执行 Pod 删除、节点不可用、下游超时和资源限制故障演练。
7. 验证 HPA 行为和缩容时在途任务安全。

## 兼容与回滚

性能优化逐项可回退。Kubernetes 引入采用与 Compose 并行验证，切流前确认相同制品和契约；回滚通过流量切回上一环境或上一稳定 Deployment，不依赖数据回退。

## 停止条件

基线不可复现、没有瓶颈证据、优化破坏正确性、Kubernetes 收益不足或缺少集群安全与回滚能力时停止。

## 退出条件

性能数据可复现，优化有量化收益；若引入 Kubernetes，滚动升级、资源限制和故障恢复已实际演练，否则 ADR 清楚记录暂不引入。
