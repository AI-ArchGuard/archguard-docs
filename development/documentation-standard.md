# 文档编写与生命周期规范

- 状态：Accepted
- 生效日期：2026-09-10
- 适用范围：七个 ArchGuard 仓库

## 核心原则

1. 一个事实只有一个权威文档；其他位置只链接，不复制。
2. 文档描述长期有效的产品、架构、契约、规范或证据，不记录逐步提示词和对话过程。
3. 任务、排期、检查清单和评审讨论进入 Issue/PR；源码实现细节进入生产者仓库。
4. 文件名按内容命名，不使用 M、D、G、V 等任务编号建立第二套路线。
5. “已实现”必须有代码和自动化证据；计划能力写“目标”或“未启用”。
6. 过期材料直接删除；重要架构决定通过新 ADR 取代，不建立无人维护的 archive。

## 文档归属

| 内容 | 位置 | 所有者 |
|---|---|---|
| 愿景、范围、路线图、术语 | `archguard-docs/product/` | 产品所有者 |
| 跨仓库上下文和容器架构 | `archguard-docs/architecture/` | 总体架构所有者 |
| 重要架构决策 | `archguard-docs/adr/` | 决策者 |
| 功能范围和验收 | `archguard-docs/requirements/` | 功能所有者 |
| 跨仓库工程规范 | `archguard-docs/development/` | 工程所有者 |
| 契约版本和兼容状态 | `archguard-docs/contracts/` | 契约生产者 |
| 阶段/发布/性能/安全证据 | `archguard-docs/reports/` | 验证执行者 |
| 模块、类、算法和适配器设计 | `<producer>/docs/technical-design/` | 实现仓库 |
| 构建和使用方式 | `<repository>/README.md` | 仓库所有者 |
| 临时任务、评审意见和实施步骤 | Issue/PR | 任务负责人 |

## 允许的文档状态

| 状态 | 含义 |
|---|---|
| `Draft` | 尚可大幅调整，不授权实现 |
| `Ready` | 范围和验收已明确，可以实现 |
| `Accepted` | 规范或决策已批准 |
| `Implemented` | 对应实现和验证已经存在 |
| `Deprecated` | 仍兼容但不再推荐使用 |
| `Superseded by ...` | 被明确的新文档或 ADR 取代 |

报告使用 `Passed`、`Failed` 或 `Closed`，不能使用模糊的“基本通过”。

## 最小结构

Feature Spec 至少包含：状态、用户结果、范围、非目标、验收标准、兼容和安全边界。Technical Design 至少包含：上下文、方案、边界、依赖、失败处理、测试、发布和回滚。ADR 至少包含：状态、背景、决策、备选、影响和重新评估条件。报告至少包含：对象版本、环境、执行命令、结果、失败项和证据位置。

## 命名和链接

- 文件使用小写 kebab-case，例如 `scanner-v0.2-feature-spec.md`。
- 路线阶段只使用“阶段 0–7”和对应版本，不创造新的里程碑编号体系。
- 相对链接优先；目录必须有 README 作为索引。
- Mermaid 图只表达文本难以清楚表达的关系，并与正文使用同一术语。
- 示例必须是合成数据，不包含密钥、真实客户源码或个人数据。

## 变更规则

- 路线变化先更新 ADR，再更新 roadmap、phase-gates 和当前 Feature Spec。
- 契约变化先改生产者 Schema/示例，再更新本库索引和消费者测试。
- 已接受 ADR 不原地改变结论；使用新 ADR 的 `Superseded by` 关系。
- 阶段报告在阶段退出时创建一次；日常测试结果留在 CI/PR，不为每次执行创建报告。
- 删除文档前用链接检查确认所有引用同时删除或迁移。

## 文档完成定义

- 所有陈述可区分当前事实和目标状态。
- 没有重复事实源、悬空链接或旧阶段编号。
- README 能从根目录导航到该文档。
- 相关代码仓库和契约所有者已同步。
- Markdown 链接、空白、YAML 和 Secret 检查通过。
