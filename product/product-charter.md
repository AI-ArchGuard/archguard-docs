## 本文解决的问题

本文只回答 ArchGuard 为谁解决什么问题、V1 应产生什么用户价值，以及如何判断产品边界和交付结果可信。V1 的详细功能与技术栈验收标准由后续 Feature Spec 定义；Scanner 结构、公共 Schema 和安全执行模型不在本文决定。

## 当前事实

- 当前只有七仓库治理、模板、最小 CI 和 M0 验收证据，没有可运行的 Platform、Scanner 或 Analyzer。
- Java/Spring、Maven、JVM 字节码和 Gradle 均未达到“已支持”标准，具体状态以[支持矩阵](support-matrix.md)为准。
- D01–D04 范围评审已确认 V1 必选项、增强项和非目标；完整产品边界仍须通过 G1。
- 当前没有用户研究、生产流量或性能基线，因此本文不把未经验证的数值写成产品事实。

## 要解决的问题

Java/Spring 团队的架构约束、实现事实和 ADR 往往分散在文档、代码评审与个人经验中。依赖方向、分层或框架使用发生漂移时，问题常在人工评审或后期集成才被发现，且结论难以稳定复现、定位证据和追踪到治理意图。

ArchGuard 要把以下闭环变成可重复、可审计的产品行为：

1. 明确一个 Project 及其 Repository 治理范围。
2. 对指定版本和 Policy 发起受控 Scan。
3. 从 Java/Spring 与 Maven 静态输入提取确定性 Fact 和最小 Evidence。
4. 用可重复的 Rule 产生 Finding，并把失败或不确定输入记录为 Diagnostic。
5. 让用户能够基于证据处理问题，并追踪规则、决策和交付证据。

## 目标用户

| 用户层级 | 典型责任 | 当前痛点 | V1 主要价值 |
|---|---|---|---|
| 主要用户：Java/Spring 技术负责人或架构师 | 定义边界、评审依赖、维护架构规则和解释例外。 | 人工评审不稳定，架构结论与证据、ADR 脱节。 | 获得确定、可定位、可重复检查的架构结果。 |
| 直接用户：Java/Spring 开发者 | 在实现和重构中遵守团队架构约束。 | 反馈晚、结论抽象，难以判断影响对象和修改方向。 | 在手动扫描结果中看到 Rule、Finding 和最小 Evidence。 |
| 次要用户：平台、质量或工程效能维护者 | 维护项目、权限、策略、审计和交付门禁。 | 工具状态、执行失败和能力范围难以统一治理。 | 获得明确状态、Diagnostic、版本和审计关联。 |

V1 优先优化单个 Java/Spring Repository 的可信治理闭环，不以跨组织规模、公开 SaaS 管理或多语言统一运营为目标。

## 核心使用场景

### V1 核心旅程

1. 用户建立或选择 Project，并登记一个获准分析的 Repository。
2. 用户选择明确的 Repository 版本、Policy 和 V1 能力，手动创建 Scan。
3. 系统返回可查询的生命周期状态；失败、部分成功和取消不得伪装为成功。
4. 用户查看按稳定规则排序的 Finding，并定位对应 Rule、影响对象和最小 Evidence。
5. 用户单独查看解析、配置、资源或执行 Diagnostic，避免与违规结论混淆。
6. 用户在 ArchGuard 之外决定修复、豁免或补充 ADR；V1 不自动修改目标仓库。

### 后续旅程

- PR 场景可在 V1 闭环稳定后提供自动触发和有限反馈。
- MCP 可在权限、审计和稳定查询契约完成后提供只读上下文访问。
- AI 可在确定性事实、引用和评估基线完成后提供解释与低风险建议。
- 多技术栈分析必须以独立能力声明和验收证据进入，不从长期定位自动推导。

## 产品价值

- **可信**：相同输入、能力版本、配置和资源边界应产生可复现的规范化结果。
- **可解释**：Finding 能回到 Rule、影响对象与最小 Evidence；Diagnostic 不冒充违规。
- **可治理**：Project、Repository、Policy、Scan 和结果具有明确归属、状态与审计关系。
- **可演进**：产品能力、Analyzer 和公共契约通过版本与证据演进，不绑定 Platform 内部类。
- **诚实**：规划、目标和当前支持严格分开，未实现能力不得用于对外支持声明。

## 目标状态

### V1

- Java 源码、Spring 语义和 Maven 静态元数据形成可演示、可测试的必选分析范围。
- Project、Repository、手动 Scan、Policy、结果查询和审计形成最小产品闭环。
- 结果语义明确区分 Fact、Finding、Evidence 和 Diagnostic，并支持失败或部分成功。
- 每项 V1 必选能力都有 Feature Spec、固定样例、自动化验收、使用说明和限制说明。
- JVM 字节码与 Gradle 静态元数据作为增强项单独评估，不阻塞 V1 发布。

## 成功指标

下表定义测量方法和发布门禁，不声称当前已有测量结果。需要经验数据的阈值必须在 V1 Feature Spec 进入 Ready 前，通过固定样例和基线测试确定。

| 指标 | 测量与证据 | V1 判定原则 |
|---|---|---|
| 核心旅程可完成性 | 目标用户按文档在参考样例完成登记、手动扫描和证据查看。 | 任务清单全部可完成；体验阈值由 Feature Spec 基线确定。 |
| 结果确定性 | 对相同输入版本、能力版本、Policy 和限制重复执行并规范化比较。 | V1 黄金样例全部精确一致。 |
| Finding 证据完整性 | 校验每个 Finding 的 Rule 身份、影响对象和最小 Evidence。 | V1 验收集中覆盖率为 100%。 |
| 失败可诊断性 | 对不支持输入、解析失败、超限、取消和执行失败检查终态与 Diagnostic。 | V1 规定场景全部有明确终态和结构化诊断。 |
| 需求可追踪性 | 从 V1 需求定位架构、ADR、工程里程碑和自动化验收证据。 | 发布范围内需求覆盖率为 100%。 |
| 支持声明可信度 | 审查支持矩阵中每次升级为“已支持”的证据链接。 | 所有状态升级均有实现、测试、说明和限制证据。 |

## 防护指标与边界

| 防护项 | 不可接受结果 | 验证方向 |
|---|---|---|
| 目标仓库执行 | V1 执行 Maven、Gradle 构建、插件、任务或目标仓库代码。 | 安全测试证明只读静态输入边界。 |
| 结果真实性 | 把解析失败、缺少能力或部分结果显示为完整成功。 | 状态机、契约和失败路径验收。 |
| 数据最小化 | 默认保存凭据、无关上下文或完整源码作为 Evidence。 | 数据分类、最小 Evidence 和保留/删除测试。 |
| 权限与归属 | 用户访问未授权 Project、Repository、Scan 或结果。 | 授权、越权和审计测试。 |
| 确定性退化 | LLM 取代 Rule 形成 V1 违规判断。 | V1 不包含 AI；确定性黄金结果作为事实基础。 |
| 性能承诺 | 在没有固定负载、环境和基线时承诺吞吐或延迟。 | 先建立可复现基线，再在 Feature Spec 中设门槛。 |

## 非目标

- V1 不提供 PR 自动触发、Check 或评论反馈。
- V1 不提供 MCP 工具或面向 Agent 的无限制访问。
- V1 不提供 AI 解释、自动修复、自动提交或自动合并。
- V1 不实现 Go、TypeScript、Kotlin、Scala 或任意语言的动态插件生态。
- V1 不执行目标 Repository 的构建、脚本、插件、任务或任意命令。
- 当前产品不承诺商业化、多租户公开 SaaS、生产级组织规模或公开部署范围。
- Deploy 仓库的存在不表示已支持容器或部署配置分析。

## 已接受决策

- 长期产品方向面向多技术栈，但 V1 深度优先于语言广度。
- V1 必选分析范围是 Java 源码、Spring 语义和只读 Maven 静态元数据。
- JVM 字节码和只读 Gradle 静态元数据是 V1 增强项，不构成发布门槛。
- PR、MCP 和 AI 明确不属于 V1；确定性 Rule 是事实基础。
- 当前没有业务能力处于“已支持”，状态升级必须附带可定位证据。

上述产品章程整体仍为 Draft，须经 G1 评审后才能成为已接受边界。
