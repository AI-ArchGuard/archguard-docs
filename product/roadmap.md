# ArchGuard 产品路线图

- 状态：Accepted
- 适用范围：未来 12 个月的 V1–V5 产品结果优先级及其与 M0–M13 工程里程碑的关系
- 所有者：ArchGuard 项目所有者
- 依赖决策：产品定位、支持矩阵与产品章程草案
- 最后评审：2026-09-08（G1 产品边界评审通过）
- 取代/被取代：无

## 本文解决的问题

本文只回答 ArchGuard 应按什么顺序交付用户可感知的产品结果，以及这些结果如何依赖现有工程里程碑。它不把计划能力写成当前支持，不替代 Feature Spec，也不为尚无证据的工作承诺发布日期。

## 当前事实

- 当前只完成 M0 治理基线；所有产品和分析能力仍是未支持或目标状态。
- M1 正在拆分产品、架构、契约、安全和可开发性文档，D01–D06 属于 G1 产品边界关卡。
- GitHub Roadmap 已为 M0–M9 记录交付顺序和日期；M10–M13 仍是后续工程阶段，不在本文复制或擅自补充日期。
- G1 已确认 V1 必选项、增强项、非目标以及 V2–V5 的优先级方向；V2–V5 的详细 Feature Spec 与发布日期仍未确定。

## 版本与里程碑口径

| 名称 | 回答的问题 | 状态变化依据 |
|---|---|---|
| 产品版本 `V1`–`V5` | 用户获得了什么可感知结果，哪些能力共同构成一次产品发布？ | Feature Spec、实现、自动化验收、使用与限制说明齐备。 |
| 工程里程碑 `M0`–`M13` | 团队按什么顺序建立规范、实现、集成、部署和证据？ | 对应 Issue、提交、CI、报告和里程碑退出条件完成。 |
| 关卡 `G1`–`G4` | 哪类产品或架构边界已足够清楚，可以安全进入下一组设计或实现？ | 关卡检查项有明确评审结论和开放问题去向。 |

- 一个产品版本通常依赖多个工程里程碑，一个工程里程碑也可能为多个产品版本提供基础。
- 完成某个 `M` 不自动发布某个 `V`；路线图中出现某项能力也不表示“已支持”。
- 产品版本不继承工程里程碑日期。日期与负责人由 GitHub Roadmap 和对应 Issue 管理。
- V1 发布门槛只计算“V1 目标”；V1 增强项未完成时不得对外声称已支持，但不阻塞 V1。

## 路线图原则

1. 先形成手动、确定、可验证的核心闭环，再增加自动触发和外部入口。
2. 确定性 Fact、Rule、Finding 和 Evidence 先于 MCP 与 AI。
3. 每个新入口先完成权限、审计、失败和资源边界，再扩大使用场景。
4. 多技术栈扩展以真实需求、独立 Analyzer 和验收证据为前提，不按仓库实现语言推导支持。
5. 未通过前一版本的关键退出证据时，后续版本可以研究和设计，但不得替代前一版本的交付门槛。

## 未来 12 个月的优先级

规划窗口为 2026-09-08 至 2027-09-07。下表表达结果顺序，不承诺所有版本都在窗口内发布；只有对应 Feature Spec 与工程里程碑确认后，产品版本才获得发布日期。

| 优先级 | 产品版本 | 用户结果 | 必选能力 | 明确不包含 | 退出证据 |
|---|---|---|---|---|---|
| P0 | V1：Java/Spring 可信治理闭环 | 用户能登记 Java/Spring Repository，手动扫描指定版本，并依据可重复的 Finding 与 Evidence 处置架构问题。 | Project/Repository 治理、手动 Scan、Policy 与确定性 Rule、Java 源码、Spring 语义、只读 Maven 静态元数据、结果与 Diagnostic 查询。 | PR 反馈、MCP、AI、其他语言、自动修改，以及目标仓库构建或脚本执行。 | D14 Feature Spec、版本化契约、合成样例、黄金测试、权限/安全测试、端到端验收、使用与限制说明。 |
| P1 | V2：评审流程内反馈 | 用户在 PR 工作流中获得受控、幂等且可审计的扫描状态和有限反馈，不必手动搬运结果。 | GitHub App 最小权限、Webhook 验证与幂等、增量扫描触发、Check 或有限评论、失败降级与审计。 | 自动修改代码、自动提交、自动合并、长期 PAT 和任意仓库脚本。 | GitHub 权限矩阵、威胁分析、重放/限流测试、PR 端到端样例和回滚说明。 |
| P2 | V3：安全只读上下文访问 | 获准用户或工具能在明确范围内查询代码、依赖、Finding、ADR 和 CI 证据。 | MCP 只读工具目录、严格输入/输出 Schema、身份传播、最小权限、限流、审计和安全退出。 | 写 Repository、任意 Shell、直接访问业务数据库、无限制代理循环和跨 Project 查询。 | Tool 契约测试、授权/越权测试、安全评估、可观测证据和使用限制。 |
| P3 | V4：有证据的 AI 解释 | 用户获得引用确定性结果和 ADR 的解释、归纳与低风险建议，并能识别拒绝或不确定结论。 | 版本化评估集、严格输出 Schema、最小上下文检索、证据引用、模型/Prompt 版本、成本与安全门禁。 | 用 LLM 代替 Rule、把 AI 设为唯一质量门禁、无证据判断、自动修改或自动合并。 | 固定 Evals、引用真实性与拒答测试、安全零容忍项、成本/延迟报告和人工复核样例。 |
| P4 | V5：经验证的多技术栈扩展 | 用户能对至少一个 V1 之外的技术栈获得独立、明确且可验证的分析能力，并在条件成熟时查看跨 Analyzer 关系。 | 需求验证、独立能力声明、单独 Feature Spec、技术栈版本矩阵、Analyzer 验收；跨技术栈视图须至少依赖两个已支持 Analyzer。 | 同时承诺 Go 与 TypeScript、因 JVM 或部署仓库存在而推导支持、未经批准的动态插件系统。 | 新产品决策、独立样例与黄金测试、契约兼容测试、支持矩阵证据；当前尚无对应工程里程碑承诺。 |

## V1 增强项处理

- JVM 字节码和只读 Gradle 静态元数据保持 V1 增强项，必须在 V1 必选闭环稳定后评估。
- 增强项可以作为 V1.x 或后续版本的候选，但必须通过明确的产品决策更新路线图和支持矩阵。
- 未完成的增强项不得静默转成 V1 发布门槛，也不得仅因存在实验实现而升级为“已支持”。
- 增强项若影响 Fact 优先级、执行安全或公共契约，须先通过相应 ADR 与 G2/G3 评审。

|---|---|---|

| G2 架构边界 | Platform、Scanner、Registry、Analyzer 和进程边界。 | 未通过时不冻结公共 Schema，也不估算跨语言扩展交付。 |

## 与 M0–M13 的映射

本表只说明主要贡献，不改变各阶段提示词或 GitHub Roadmap 的日期、负责人和退出条件。

| 工程里程碑 | 主要工程结果 | 服务的产品版本 | 关系说明 |
|---|---|---|---|
| M0 | 七仓库治理、模板、最小 CI 和远程治理证据。 | 全版本基础 | 已完成；不构成任何产品能力已支持。 |
| M1 | 产品、需求、总体架构、契约、安全、ADR 和追踪边界。 | V1 为主，支撑 V2–V5 | 通过 G1–G4 后才允许进入 V1 实现。 |
| M2 | Java Platform 模块化单体骨架与最小项目垂直切片。 | V1 | 建立产品控制面，不提供真实分析。 |
| M3 | Repository 登记、Scan 状态机和 Fake Scanner 闭环。 | V1 | 验证产品流程，不代表 Scanner 能力已支持。 |
| M4 | Java Scanner MVP、确定性分析和版本化契约。 | V1 | 提供分析核心，仍需与 Platform 集成。 |
| M5 | Platform、Scanner、Samples 的真实异步扫描集成。 | V1 | 形成 V1 端到端主路径与清理、重试证据。 |
| M6 | GitHub App PR 集成。 | V2 | 在 V1 结果之上增加评审流程入口。 |
| M7 | 基于真实数据的消息与可靠性演进。 | V2 与跨版本 | 允许结论为保留数据库队列；不是独立产品版本。 |
| M8 | Go MCP Gateway 与只读工具。 | V3 | Gateway 使用 Go 不表示支持 Go 源码分析。 |
| M9 | Evals 基线与安全中心。 | V4 前置与跨版本 | 先建立评估证据，不等于 AI 产品能力已交付。 |
| M10 | AI 架构评审解释层。 | V4 | 依赖 V1 确定性事实、V3 安全查询边界和 M9 评估基线。 |
| M11 | 可重复部署、CI/CD、备份、恢复和回滚。 | 跨版本发布保障 | 强化可运行性，不表示支持部署配置分析。 |
| M12 | 性能基线、瓶颈优化与有条件的 Kubernetes 决策。 | 跨版本容量保障 | Kubernetes 可以被明确拒绝，不构成产品版本目标。 |
| M13 | 全工作区交付审计与发布准备。 | 已完成版本的证据审计 | 不新增大型功能，不替代各版本自身验收。 |

V5 当前没有对应的 M0–M13 实现里程碑。只有完成需求验证、确定首个扩展技术栈并接受独立 Feature Spec 后，才新增或调整工程里程碑；不得把 M11–M13 误写成 V5 多技术栈交付。

## 目标状态

- README、支持矩阵、Feature Spec、Issue 和发布说明使用同一版本口径。
- 每个产品版本都有用户结果、必选能力、非目标、依赖和可定位退出证据。
- GitHub Roadmap 管理工程日期，本文件管理产品结果顺序，两者通过链接和追踪矩阵关联而不复制事实。
- 版本优先级可由新证据调整，但已接受产品或架构结论通过新的决策记录取代，不原地掩盖变化。

## 非目标

- 不承诺 V2–V5 的发布日期、商业版本号、定价或公开 SaaS。
- 不把产品版本与单个仓库、组件、编程语言或工程里程碑一一对应。
- 不在路线图中冻结 Scanner、Analyzer Registry、进程协议、公共 Schema 或部署拓扑。
- 不因计划出现就把 PR、MCP、AI、Go、TypeScript、JVM 字节码或 Gradle 描述为已支持。
- 不用 Kubernetes、微服务或消息中间件作为产品进展的替代指标。

## 已接受决策

- V1 深度支持 Java/Spring 的必选闭环，PR、MCP 和 AI 依次置于 V1 之后。
- 确定性分析和证据先于外部工具入口与 AI 解释。
- V1 增强项不阻塞 V1，也不自动继承到某个后续版本。
- V1–V5 表示产品结果优先级，M0–M13 表示工程交付顺序，二者不等价。
- V5 首个扩展技术栈和对应工程里程碑保持开放，须由需求与验收证据驱动。

上述 V1–V5 优先级已在 G1 评审中成为已接受产品路线图；详细范围和日期仍须逐版本评审。
