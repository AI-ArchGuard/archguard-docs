# ArchGuard 能力地图

- 状态：Accepted
- 适用范围：ArchGuard 产品能力的分类与边界
- 所有者：ArchGuard 项目所有者
- 依赖决策：产品定位与公共术语草案
- 最后评审：2026-09-09（同步 G2 架构边界；G1 能力分类不变）
- 取代/被取代：无

## 本文解决的问题

本文只回答一项能力属于平台治理、分析、契约扩展还是部署运行。能力是否已经交付由独立支持矩阵记录；列入本地图不等于当前支持或承诺进入某个版本。

## 当前事实

- 当前仅完成 M0 治理与文档基线，没有可运行的产品或 Analyzer 能力。
- 现有仓库 README 已区分 Platform、Scanner、MCP Gateway、Deploy、Samples 和 Evals 的高层职责。
- 组件、进程、仓库和 Analyzer Registry 关系已通过 G2；公共字段、Rule 职责和安全默认值已通过 G3。

## 分类原则

| 类别 | 回答的问题 | 归类边界 |
|---|---|---|
| 平台治理能力 | 团队如何管理治理对象、策略、执行和结果？ | 默认与被分析语言无关，不负责解析源码。 |
| 通用分析能力 | 不同 Analyzer 共同需要哪些确定性分析行为？ | 处理受控输入并产生分析结果，不管理产品业务状态。 |
| 语言与领域分析能力 | 对哪种语言、框架或工程制品理解到什么程度？ | 每项都必须单独声明技术栈、版本和限制。 |
| 契约与扩展能力 | 平台和分析能力如何被描述、组合和演进？ | 定义边界与兼容，不等同于动态插件实现。 |
| 部署与运行能力 | 能力如何被安全、可观测、可回滚地运行？ | 负责运行条件，不等同于分析部署配置的 Analyzer。 |

## 平台治理能力

这些能力原则上与 Java、Go 或 TypeScript 无关。

| 能力域 | 主要职责 | 明确排除 |
|---|---|---|
| 身份与授权 | 用户、组织、项目成员、资源归属和最小权限。 | 语言解析、规则求值。 |
| 项目与仓库治理 | 登记 Project 与 Repository，维护状态和治理范围。 | 直接执行目标仓库代码。 |
| 扫描编排 | 创建 Scan、管理生命周期、幂等、取消、重试和结果关联。 | 把 Platform 内部模型作为 Scanner 契约。 |
| Policy 管理 | 选择 Rule、参数、严重性和适用范围。 | 在产品控制面内实现每种语言的执行器。 |
| 结果与证据 | 查询、筛选、追踪 Finding、Evidence 和 Diagnostic。 | 默认保存完整源码。 |
| 决策与追踪 | 关联需求、ADR、规则、里程碑和验收证据。 | 用 ADR 替代可执行规则。 |
| 审计与报告 | 记录身份、范围、操作、结果版本和关键安全事件。 | 记录凭据、完整源码或隐藏推理。 |
| 外部集成 | 通过受控 API、PR 反馈或只读工具提供能力。 | 默认外部写操作或任意 Shell。 |
| AI 辅助 | 基于已验证事实解释、归纳和提出低风险建议。 | 取代确定性 Rule 或绕过 Schema、权限与业务校验。 |

## 通用分析能力

| 能力域 | 主要职责 | 语言关系 |
|---|---|---|
| 输入发现与验证 | 识别受控输入、规范化路径、校验配置与限制。 | 入口通用，具体文件识别可由语言能力扩展。 |
| 事实抽取 | 从输入生成确定、稳定排序的 Fact 和 Evidence。 | 统一原则，抽取逻辑通常与语言或领域相关。 |
| 关系建模 | 构建依赖边、层级、组件或其他可重复分析结构。 | 模型原则通用，语义来自具体 Analyzer。 |
| Rule 求值 | 在明确 scope 和配置下执行确定性约束并产生 Finding。 | 执行框架通用，规则可能语言无关或语言特定。 |
| 诊断与部分结果 | 区分解析、配置、超限和执行问题，保留可用结果。 | 行为通用，错误细节由 Analyzer 提供。 |
| 资源边界 | 限制输入规模、时间、内存、并发和输出大小。 | 通用安全要求，阈值可按能力配置。 |

## 语言与领域分析能力

| 能力族 | 典型范围 | 产品方向 |
|---|---|---|
| Java 源码分析 | 类型、包、调用或依赖关系及源码级 Evidence。 | V1 深度支持方向。 |
| JVM 制品分析 | 字节码、类路径和已编译依赖关系。 | V1 增强项，不是发布门槛。 |
| Spring 语义分析 | Bean、注入、分层、模块和框架配置关系。 | V1 深度支持方向。 |
| 其他语言分析 | Go、TypeScript、Kotlin、Scala 等语言前端与规则。 | V1 之外的候选，不是当前支持。 |
| Maven 元数据分析 | 只读解析 POM 等静态元数据，不执行目标构建。 | V1 必选方向，具体字段范围待 Feature Spec。 |
| Gradle 元数据分析 | 只读解析可安全识别的静态元数据，不执行插件或任务。 | V1 增强项，不是发布门槛。 |
| 其他工程制品分析 | 依赖清单、容器或部署配置。 | 单独声明范围；不因 Deploy 仓库存在而自动支持。 |
| 跨技术栈关联 | 把多个 Analyzer 的事实连接为跨仓库视图。 | 长期方向，依赖稳定契约和至少两个已支持 Analyzer。 |

## 契约与扩展能力

| 能力域 | 主要职责 | 后续冻结位置 |
|---|---|---|
| Analyzer 能力描述 | 声明身份、版本、输入类型、能力、配置和可用性。 | Analyzer capabilities 设计切片。 |
| 扫描请求与结果 | 传递输入引用、限制、配置、状态和输出。 | 版本化 scan contract。 |
| 公共结果语义 | 区分 Fact、Finding、Evidence 和 Diagnostic。 | 统一结果模型。 |
| 版本与兼容 | Schema 版本、未知字段、兼容范围和迁移策略。 | scan contract 与 ADR。 |
| 多 Analyzer 组合 | 能力选择、结果归并、冲突和部分成功语义。 | Scanner runtime 与 scan contract。 |

列出这些能力只预留稳定扩展边界，不承诺 V1 实现动态插件系统。

## 部署与运行能力

| 能力域 | 主要职责 | 明确排除 |
|---|---|---|
| 打包与发现 | 让已批准能力可被部署、配置和识别。 | 从不可信仓库自动加载可执行插件。 |
| 执行隔离 | 控制进程、文件、网络、构建和系统调用边界；V1 不执行目标构建。 | 默认信任目标仓库。 |
| 资源与生命周期 | 限制 CPU、内存、时间、并发，处理取消与清理。 | 无上限执行。 |
| 可观测与审计 | 记录版本、能力、耗时、结果摘要和安全事件。 | 记录凭据或不必要的源码。 |
| 兼容与回滚 | 记录可部署制品、契约版本、发布和回滚顺序。 | 通过修改已发布迁移或 ADR 隐藏不兼容。 |

“部署与运行能力”负责运行 ArchGuard；“部署配置 Analyzer”若未来存在，属于语言与领域分析能力。两者不得混用。

## 目标状态

- 每项产品需求可定位到一个主要能力类别，跨类别依赖被明确标出。
- 每个 Analyzer 只声明实际提供且可验证的能力。
- 支持矩阵、Feature Spec 和验收证据引用本地图，而不复制分类规则。

## 非目标

- 不分配七仓库内部模块或类级所有权。
- 不决定 Registry 归属、进程协议、动态加载或具体部署拓扑。
- 除“V1 不执行目标构建”的已确认范围约束外，不冻结公共 Schema、Rule 执行模型或其他安全默认值。
- 不为 V2–V5 安排优先级；该工作属于产品路线图。

## 已接受决策

- Platform 初期保持模块化单体，不为展示而拆分微服务。
- Scanner 输出必须使用独立、版本化且不依赖 Platform 内部类的契约。
- 确定性规则作为事实基础，LLM 只承担解释、归纳和低风险建议。
- V1 以 Java 源码、Spring 语义和 Maven 静态元数据为必选分析范围；JVM 字节码与 Gradle 静态元数据为增强项；PR、MCP 和 AI 能力不进入 V1。

能力分类及 V1 归属已在 G1 评审中接受；组件所有权、Registry 和 V1 进程边界已在 G2 接受，公共契约、Rule 执行语义和安全默认值已在 G3 接受。

## 开放问题

- V1 的 Java 源码与 Spring 语义覆盖到何种深度？
- Maven 静态元数据需要覆盖哪些元素，无法静态判断时如何诊断？
- JVM 字节码与 Gradle 增强项分别采用什么进入条件？
- 哪些通用能力由 Scanner runtime 提供，哪些由 Analyzer 自行实现？
- 跨技术栈关联何时具备足够事实模型和验收样例？
