## 评审结论

G1 通过。D01–D06 状态统一为 Accepted，允许进入 G2 架构边界设计。

G1 只冻结产品边界和优先级，不冻结 Scanner 内部结构、Analyzer Registry 归属、进程模型、公共扫描 Schema、Rule 执行所有权或安全隔离实现。

## 已接受决策

### 1. 长期定位

- ArchGuard 长期定位为面向多技术栈的软件架构治理平台。
- “多技术栈”是长期方向，不表示当前或 V1 已支持多个语言和框架。
- V1 选择 Java/Spring 深度优先，不追求语言广度。

### 2. V1 范围

- V1 必选分析范围是 Java 源码、Spring 语义和只读 Maven 静态元数据。
- V1 必选产品闭环包括 Project/Repository 治理、手动 Scan、Policy 与确定性 Rule、结果与 Diagnostic 查询。
- JVM 字节码和只读 Gradle 静态元数据是 V1 增强项，不阻塞 V1 发布。
- V1 不执行目标 Repository 的构建、脚本、插件、任务或任意命令。

### 3. 当前与未来支持

- 当前没有业务或分析能力处于“已支持”；实现、自动化验收、使用和限制证据齐备后才能升级状态。
- PR 反馈、MCP 只读查询和 AI 解释明确不属于 V1。
- Kotlin、Scala、Go、TypeScript、部署配置和跨技术栈关联仍是后续候选，不因现有仓库或实现语言自动获得支持状态。

### 4. 路线图优先级

产品结果顺序确认为：

1. V1：Java/Spring 可信治理闭环。
2. V2：PR 评审流程内反馈。
3. V3：安全只读 MCP 上下文访问。
4. V4：基于确定性证据和 Evals 的 AI 解释。
5. V5：经需求验证的第二技术栈及有条件的跨 Analyzer 关联。

V1–V5 是产品结果顺序，M0–M13 是工程交付顺序，二者不等价。V2–V5 的详细 Feature Spec 和发布日期仍须单独评审。

## 目标状态

- 后续需求、架构、ADR、Issue 和 README 使用 D01–D06 的产品口径。
- G2 只在已接受产品边界内决定 Platform、Scanner、Registry、Analyzer 和进程关系。
- G3 在 G2 通过后冻结版本化契约、结果语义、Rule 职责和不可信 Repository 安全默认值。
- G4 通过 D14–D16 把 V1 产品边界转成可开发、可测试和可追踪的交付范围。

## 非目标

- 不在 G1 决定 Java/JDK、Spring 或 Spring Boot 的精确版本矩阵。
- 不决定具体 Fact、Rule、Finding、Evidence 字段和错误码。
- 不选择 JavaParser、ASM、ArchUnit、进程协议或动态插件方案。
- 不承诺 V2–V5 日期、商业化、多租户公开 SaaS 或生产规模。
- 不把 V5 等同于 Go、TypeScript 或同时支持所有候选技术栈。
